# PR 规范

PR 是审查单元，而不是工作单元。为审查者优化，而不是为作者优化。

**权衡：** 拆分工作需要纪律。回报是更快的审查、更干净的历史和更容易的回滚。

## 1. 每个 PR 只做一件事

**如果你无法用一句话概括 PR，就拆分它。**

- 修复 bug 的 PR 不应该同时重构周围的代码。
- 新增功能的 PR 不应该同时修复无关的 lint 错误。
- 重构和行为变更必须分开成独立的 PR——永远如此。
- 如果在开发功能时发现了 bug，先在独立分支修复它。

检验标准：审查者能独立批准其中任何一半吗？如果可以，就应该是两个 PR。

## 2. 提交信息解释原因

**diff 展示了什么变化。信息解释为什么变化。**

- 第一行：祈使语气，不超过 72 个字符。（"为 /auth 端点添加速率限制"）
- 如果原因需要超过一行，空一行后加一段简短说明。
- 不要描述 diff（"将 X 从 Y 改为 Z"）——diff 已经做了这件事。
- 相关时引用 issue 编号，但不要依赖它们提供上下文。

坏：`fix stuff`
坏：`在配置中将超时从 30 改为 60`
好：`增加认证超时以处理缓慢的 LDAP 响应`

## 3. 保持 PR 可审查

**目标不超过 400 行改动。硬性上限 800 行。**

- 大型 PR 会被敷衍通过。小型 PR 会得到真正的反馈。
- 如果 PR 必须很大，添加描述说明结构——先读什么，什么是机械性的，什么是有意义的。
- 不要在不标注说明的情况下用自动生成的文件或第三方代码填充 PR。
- 在请求审查前压缩 fixup 提交。像"fix"、"fix fix"、"typo"这样的历史是在浪费审查者的时间。

## 4. 审查前清理

**在占用他人时间之前，先自己审查 diff。**

- 从头到尾阅读 diff，把自己当成审查者。
- 删除调试日志、注释掉的代码和应该放在 issue 里的 TODO 注释。
- 验证 PR 描述与 diff 中实际内容一致。
- 在推送请求审查之前，确认 CI 在本地通过。
