# API 设计

API 是一种承诺。设计它要让它难以被误用、易于理解且便于履行。

**权衡：** 精简的 API 限制了灵活性。这正是重点——约束防止耦合。

## 1. 让成功之路显而易见

**使用 API 的正确方式应该是最简单的方式。**

- 常见情况应该需要最少的参数。
- 可选的复杂性应该是选择加入的，而不是选择退出的。
- 如果调用方总是绕过某个参数，重新思考它。
- 如果 API 需要阅读文档才能正确使用，说明默认值是错误的。

## 2. 暴露行为，而非实现

**调用方不应该需要知道它是如何工作的。**

- 不要在接口中泄露内部类型、状态机或实现类。
- 如果改变实现需要改变调用方，说明边界划分在了错误的地方。
- 优先传递值而不是传递带有内部调用方法的对象。
- 返回能传达结果的最小类型——而不是最丰富的可用类型。

## 3. 为调用约定设计，而非为实现设计

**先写调用方代码，再实现。**

- 在编写函数之前，先写调用它的代码。
- 如果调用方看起来很别扭，重新设计函数。
- 如果调用方总是成对调用两个函数，合并它们。
- 如果调用方总是在使用返回值之前检查它，将其编码到类型中。

## 4. 新增是安全的。修改不是。

**扩展，而不是修改。**

- 新增一个新的可选参数通常是安全的。改变现有参数的含义永远不安全。
- 在删除之前先废弃。给调用方一条迁移路径。
- 如果必须破坏接口，在一个地方做（版本升级、重命名）——不要在多次改动中逐渐进行。
- 内部代码并不是"可以随意破坏的"——未来的维护者也是调用方。
