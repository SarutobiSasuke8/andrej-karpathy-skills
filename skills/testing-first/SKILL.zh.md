# 测试优先

先写测试，再写修复。一个能重现问题的测试证明你理解了它；一个事后通过的测试证明你解决了它。

**权衡：** 会增加前期时间。对于非琐碎的 bug 和新行为值得这样做。显而易见的一行修改可跳过。

## 1. 先重现，再修复

**在有一个失败测试之前，不要动代码。**

- 编写一个因 bug 报告中描述的确切原因而失败的测试。
- 如果你无法写出失败测试，说明你还没理解这个 bug。
- 在修改任何内容之前，运行测试确认它确实失败。
- 然后做最小的改动让它通过。

```
1. 编写测试 → 验证：测试失败
2. 修复代码 → 验证：测试通过
3. 运行完整测试套件 → 验证：无回归
```

## 2. 一个测试对应一个行为

**每个测试只断言一件事。精确命名。**

- 测试名称应能完成这个句子："它应该……"
- 实际可行时每个测试一个断言。如果多个断言都属于同一行为，可以放在一起。
- 不要测试实现细节——测试可观察的行为。
- 如果重命名一个变量导致测试失败，说明测试测错了东西。

## 3. 测试与被测代码放在一起

**并置减少漂移。**

- 将测试放在被测代码的同一目录下，或采用镜像的平行目录结构。
- 移动文件时，同时移动其测试。
- 删除文件时，同时删除其测试。
- 孤立的测试是谎言——删除它们。

## 4. 不要为测试写测试

**不要过度规范的 fixture，不要需要自身测试的测试工具。**

- 对于非琐碎状态，优先使用简单的内联设置而非共享 fixture。
- 如果你的测试辅助函数比测试本身还长，将其折叠为内联。
- 避免 mock 你不拥有的东西——在足够快的情况下使用真实实现。
- 一个慢但真实的测试胜过一个快但测试 mock 的测试。
